## Accent wipe
The design was checked first: the export of 2026-11-01 is current, and its motion has not changed since 2026-10-28. The owner then dropped the stagger and the scroll-driven reveal as too risky.

- One wipe on load on the header and every block at the same time (owner's decision). Each contact button and each card wipes on its own, on every width.
- Once per page load, and a reload plays it again (owner's decision). `RevealOnce` sets `data-revealed` on `<html>` after the wipe, and the shutter rule needs that attribute to be absent. JavaScript only switches the decoration off.
- `.reveal` and `.reveal-left` in `globals.css`. The photo stays under the shutter and is fully visible at 850 ms (owner's decision).
- [[Home Page Handoff]] and the spec record the deviations from the design.

Detail: [[2026-10-30-home-motion]].

## Notes on the wipe
- `overflow: hidden` from `tokens.css` makes a block its own scroll container, so `view()` never follows the page. Measured in Chromium 156 and WebKit 27.2; the prototype has the same rule. The project uses `clip`.
- LCP does not see the shutter: a test page in Chromium reported 8 ms with and without it. Task 2 records the real time instead.
- A language switch turned out to be client navigation, not the full load `LocaleMenu` described: the root layout remounts and clears the attributes of `<html>`, so `RevealOnce` keeps a module variable and uses a layout effect. See [[Localization]].
- The attribute check in the selector raised its specificity above `.reveal-left` and every shutter went right. The alternation test caught it, and `:where` fixed it.
- A frame-by-frame e2e test did not catch `useEffect` in place of `useLayoutEffect`: the timing is not deterministic. A unit test reads the attribute in a sibling's layout effect, and that one fails on the broken version.
- `javaScriptEnabled: false` lets the e2e tests read the wipe however long the page takes, because nothing switches it off.

## Verification
Lighthouse on the local production build, in a browser without extensions: desktop 100 on all four, mobile 95, 100, 100, 100. Numbers and experiments: [[2026-10-30-home-motion]].

- The WhatsApp button moved to `#188842`, 4.53:1 with white, to reach 100 in Accessibility (owner's decision). It replaces the official green of 2026-10-30.
- One 3 px focus ring on every link and button, a focus indicator in forced colors mode, the visible text inside every accessible name, `fetchPriority="high"` on the photo.
- On Vercel, `/en`: desktop 100 on all four, mobile 96, 100, 100, 100. Runs differ by under 40 ms, so deployments can be compared.
- With real throttling the photo waited behind three preloaded fonts of the same priority, 1453 ms for 18 KB. Now only the Latin file of Geist is preloaded (owner's decision).
- `experimental.inlineCss` stays on (owner's decision, [[ADR-0011 Inline CSS]]): turned off, it doubled FCP under real throttling on Vercel, 921 to 1862 ms.
- Mobile stops at 98 (owner's decision): the last candidate would swap the Hero title visibly, and the gap to 100 lives only in the simulation.

## Notes on verification
- The first reports of the owner came from `next dev` with extensions on. The second ones were a production build, still with LastPass running in incognito: a single task of 561 ms made the mobile TBT 490 ms. Mobile Performance was 81 there and 94 in a clean browser.
- The result of 97 with `inlineCss` was one measurement and did not repeat. Three builds gave an LCP of 2562, 2835 and 2987 ms: the simulation moves by about 250 ms between builds, so one build proves nothing.
- Lighthouse's mobile LCP is a model: the browser painted the photo at 108 ms, real throttling gave 1636 ms and the simulation about 3000 ms. The local server speaks HTTP/1.1, which is part of the gap.
- Playwright's `hasText` does not read `<style>`, and `innerText` adds spaces between flex items that the accessible name does not have. Both made a test wrong: `textContent` fixed them.

- The font change gave mobile 98, 100, 100, 100 on Vercel and desktop 100 on all four. A merge of `develop` into `feature/main-page` brought `inlineCss` back, because the two branches had diverged through squash merges, so that deployment measured the fonts alone. `e2e/home.spec.ts` was red because of it. The accident separated the two effects, which one deployment would have hidden.
- A local build showed `inlineCss` as a bad trade and Vercel showed the opposite: a local connection has no latency, so a render-blocking file costs nothing there.
